# 应用设计（Week 5 挑战 4）

> 这不是 Week 3 skill 的包装，而是一个**新东西**：一个任何人打开浏览器就能用的页面，
> 背后是本地服务器 + 真的 DeepSeek 调用 + Week 3 的 `history.db`。

## 1. 用户在页面上做什么、拿回什么

**做**：写一个问题（中文即可，例如「加州人号的船长是谁？当晚他做了什么？」）。
页面给了 5 道示例题可以直接点。除此之外没有别的操作——不上传文件、不选表、不写 SQL。

**拿回**（页面上从上到下）：

| 位置 | 内容 | 为什么给 |
|---|---|---|
| 结论条 | 「卷宗有此记载，查得 N 行」或「这本卷宗里没有，命中 0 行」 | 一眼看出是有据还是拒答 |
| 回答 | 书记官的话，逐条带 `[id]` | 这就是交付物 |
| 引证 | `[24] [25] [30] …` 小标签 | 便于核对，未返回的行号标红 |
| 依据 | 查询真正返回的行（行号/日期/文献/位置/事实/存疑） | **审计**：回答只能来自这里 |
| 检索过程 | 模型写的 SQL 与它的检索说明 | **审计**：看出它到底查了什么 |
| 页脚元信息 | 模型名、调用次数、耗时、tokens、返回行数 | 说明这是真调用，花了多少 |

关键设计决定：**把"依据"和"查询"直接摊给用户看**。Week 3 的 rubric 要求 G 有据，
但这个应用不只是让模型"显得有据"，而是把证据摆在同一个屏幕上，用户随时可以反驳它。

## 2. 与示例 `demo-building-app` 的关系：它哪里不对

示例本身写得很好（标准库、极简、注释清楚），但它有一个教学上的陷阱：

```python
def ask_model(image: bytes) -> dict:
    """THE ONE SPOT TO REPLACE. ... This demo does not call any model."""
    return json.loads(FIXTURE.read_text(encoding="utf-8"))
```

README 自己写着 **"It looks smart. It is a fixture."**——每张照片都得到同一句答复，
而页面上只有一个角落徽章 `model: fixture`。也就是说：**真模型与假模型在界面上几乎无法区分**。
对一次课堂演示来说，这是最容易翻车的地方（演示时网络断了、密钥过期，观众根本看不出来）。

Week 5 的做法是把这件事反过来：

1. **不复制示例的交互。** 示例是"丢一张照片 → 认一座楼"，本项目是"问一个问题 → 查一段卷宗"。
   数据、问题、输出形态都不同，连前端结构也不一样（示例是照片对 + 大字名，本项目是结论条 + 台账表 + SQL）。
2. **替身永远自报身份。** `model.source` 只有两个取值：`deepseek` 或 `fixture`。
   是 `fixture` 时页面顶部亮黄条、命令行启动横幅写明、响应里 `model.name` 就是
   `offline fixture (not a model)`。**没有任何一条路径能让替身冒充模型。**
3. **替身只替模型，不替数据库。** 存档里只有本该由模型产出的两段内容（写查询、落笔），
   SQL 仍然真跑在 `history.db` 上——页面上的行是真档案行。
4. **不会的就说不会。** 离线替身只存了 5 道题，问别的直接 `409 fixture_miss`，
   不会拿最相近的一条糊弄。
5. **没有密钥时宁可失败。** `WEEK5_MODE=deepseek` 而密钥缺失时，`model.py` 直接抛
   `ModelError("...refusing to pretend a model answered")`，绝不静默退回替身。

## 3. 三步流水线（`app/clerk.py`）

```
用户问题
   │
   ├─ 第 1 步 写查询 ──→ DeepSeek（json_object）
   │      输入：真实的 CREATE TABLE 语句 + 行数 + 截断索引（id/日期/出处/前 70 字）
   │      输出：{"sql": "...", "why": "...", "out_of_scope": false}
   │
   ├─ 第 2 步 真查库 ──→ SQL 守卫 → 只读连接 → 行
   │      （这一步**没有模型**；行是 SQLite 给的）
   │
   └─ 第 3 步 落笔 ──→ DeepSeek（json_object）
          输入：问题 + 检索说明 + **只包含第 2 步那些行的 JSON**
          输出：{"answer": "...", "verdict": "...", "cited_ids": [...]}
```

为什么分两步而不是"把全库塞进上下文让模型直接答"：

- **可审计**：中间那条 SQL 是模型意图的书面证据，用户能读懂、能质疑。
- **可验证**：第 3 步的输入被严格限制在检索结果内。`code/check_app.py` 的 C 段用桩替身
  抓下提示词，断言「第 24 行的内容在」且「未被检索到的第 4 行内容**不在**」。
  这是一条可以被机器检查的"有据"定义，而不是一句口头承诺。
- **省 context**：索引是截断的（前 70 字），全文只在 SQL 命中时才进上下文。

## 4. 三层防线（`app/archive.py`）

模型写的 SQL 是不可信输入。防线是叠起来的，任何一层单独失效都还有后手：

| 层 | 手段 | 失效时 |
|---|---|---|
| 1 | 必须 `SELECT`/`WITH` 开头，且只许一条语句（`;` 直接拒） | |
| 2 | 出现 `INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/ATTACH/PRAGMA/REPLACE INTO` 等词即拒 | |
| 3 | 连接以 `file:...?mode=ro` 打开 | 1、2 都被绕过时，SQLite 自己拒绝写 |

第 3 层才是真正的保证：`check_app.py` 的 A 段真的去执行 `INSERT`/`UPDATE`/`DELETE`/`DROP`，
并断言四次都被 SQLite 挡回。**卷宗不会因为模型抽风而被改坏。**

另外：结果用 `fetchmany()` 取，最多 60 行（`WEEK5_MAX_ROWS`），**不改写模型的 SQL**
（改写 SQL 会掩盖模型到底写了什么，也让"审计"失去意义）。

## 5. 引证核对

第 3 步输出 `cited_ids`，服务器核对每个 id 是否**真的在返回行里**：

- 全部命中 → `citation_check.ok = true`；
- 出现未返回的行号 → `ok = false`，页面把该标签标红，并在结论条上警告。

服务器**不修改**模型的话（改了就没人知道它原本写了什么），只把问题指出来。
`check_app.py` 的 C2 段用一个故意编造 `[999]` 的桩替身验证这条能抓到。

## 6. 配置

| 环境变量 | 默认 | 作用 |
|---|---|---|
| `DEEPSEEK_API_KEY` | 无 | 唯一必填项；**只从环境变量读**，代码里没有任何文件读取路径 |
| `DEEPSEEK_MODEL` | `deepseek-flash` | 也可用 `deepseek-v4-pro` |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com` | |
| `WEEK5_MODE` | `auto` | `auto`（有密钥就真调）/ `deepseek`（强制真调，没密钥就报错）/ `fixture`（强制离线） |
| `WEEK5_THINKING` | 关 | 打开则用思考模式（此时 `temperature` 被 API 忽略） |
| `WEEK5_MAX_ROWS` | 60 | 单次检索最多返回多少行 |
| `WEEK5_PORT` / `PORT` | 8000 | 监听端口（只绑 127.0.0.1） |
| `WEEK5_DB` | 自动探测（`week5/` → `week3&4/` → 上级） | 指向别处的卷宗，主要给自检用 |

## 7. 已知边界

- 只支持**单轮**问答：每次请求都是全新的两步调用，不保留上下文。多轮追问是 Week 6 的事。
- 写查询这一步可能写出跑不通的 SQL（列名猜错等）→ 返回 502 并把 SQLite 的报错给用户看。
  没有自动重试；宁可暴露错误，也不要偷偷用别的方式答。
- 60 行上限是硬截断，会在响应里标 `truncated: true`。
- 页面没有鉴权：服务器只绑 `127.0.0.1`，不要往外网暴露。
- 真实 API 调用需要密钥，本仓库的开发者环境没有密钥，所以**只有密钥持有者能完成这一步验证**——
  见 [`verification.md`](verification.md) 的诚实说明。
